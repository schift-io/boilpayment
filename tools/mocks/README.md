# Provider mocks

Local, dependency-free stand-ins for provider APIs so `examples/live/*` scripts can drive the
real provider SDK/HTTP code paths without keys or network access.

> **These mocks are CI regression, NOT live verification.** They never touch a real provider
> server — they only prove the code path (serialization, error mapping, signature verification)
> hasn't broken, using canned local responses. Real live verification — actually hitting
> `api.stripe.com` / `api.tosspayments.com` / `api.portone.io` / `(sandbox-)api.polar.sh` with real
> test/sandbox keys — is `boilpayment live` (`apps/cli/src/commands/live.ts`, python parity
> `examples/live/real_round_trip.py`), which a project generated by `boilpayment init` runs against
> whatever real provider keys the owner puts in `.env`. See docs/PUBLIC_SANDBOX_VERIFICATION.md "(live
> verification)" for what it proved and a real bug (Toss `listPayments` date format) it found that
> these mocks never caught.

## Toss (`tools/mocks/toss/server.mjs`)

Toss ships no official mock server (unlike Stripe's `stripe-mock`), so this is a hand-rolled
`node:http` mock of the subset of the Toss Payments API that `packages/providers/toss` calls:
`POST /v1/payments/confirm`, `GET /v1/payments/{paymentKey}`,
`POST /v1/billing/authorizations/issue`, `POST /v1/billing/{billingKey}`,
`POST /v1/payments/{paymentKey}/cancel`, `GET /v1/transactions`. Response shapes were copied from
docs.tosspayments.com/reference (fetched 2026-09-09) — see the header comment in `server.mjs` for
the two spots where the exact Toss error `code` for a scenario couldn't be confirmed from the
fetched docs and a documented approximation (`INVALID_REQUEST`) was used instead.

```bash
node tools/mocks/toss/server.mjs        # listens on TOSS_MOCK_PORT (default 12211)
```

Requires Basic auth (`test_...` secret key only — anything else gets `401 UNAUTHORIZED_KEY`) and
honors `Idempotency-Key` on billing charges and cancels (same key → same cached response).

Mock-only helper endpoints (prefixed `/__mock/` so they never collide with a real Toss path):

- `POST /__mock/authorize` — since there's no real widget/browser in this setup, this simulates
  "the customer just authorized this exact `paymentKey`/`orderId`/`amount`/`method` on the
  widget." A real `confirm` call is checked against this registration (amount mismatch → 400).
- `POST /__mock/webhook` — makes the mock POST a `PAYMENT_STATUS_CHANGED` (or other) webhook body
  to a URL you supply, so a script can exercise `TossProvider.verifyWebhook` against a real HTTP
  delivery instead of a hand-built request object.
- `GET /__mock/health` — liveness check.

See `examples/live/toss-mock.ts` / `examples/live/toss_mock.py` for a full round trip (confirm,
get, billing key issue + charge with idempotent replay, partial/virtual-account refund, webhook
verification, and a self-scheduler tick that actually charges via the mock).

## Polar (`tools/mocks/polar/server.mjs`)

Dependency-free `node:http` mock of the subset of the Polar REST API that `packages/providers/polar`
calls directly (no `@polar-sh/sdk` — see that package's header comment for why): `POST
/v1/customers/`, `POST /v1/checkouts/custom/`, `GET /v1/orders/{id}`, `GET /v1/orders/` (list),
`GET`/`PATCH`/`DELETE /v1/subscriptions/{id}`, `POST /v1/refunds/`, `POST /v1/events/ingest`.
Response shapes were copied from polar.sh/docs/api-reference (fetched 2026-09-09 — `docs.polar.sh`
301-redirects there now). See the file's header comment for one documented simplification: real
Polar checkouts complete on Polar's own hosted page, which this API-only mock can't simulate, so
`POST /v1/checkouts/custom/` synthesizes the resulting Order (and Subscription, for a recurring
product) immediately instead of leaving the checkout `open`. Three fixed products are pre-seeded
(`prod_sub_basic`, `prod_sub_pro`, `prod_onetime_pack`) since there's no products-create endpoint
in scope.

```bash
POLAR_MOCK_PORT=12213 node tools/mocks/polar/server.mjs   # default port 12213
```

Requires `Authorization: Bearer polar_oat_test_...` (else `401`); in-memory state.

Mock-only control endpoint:

- `POST /__mock/webhook` — `{ url, secret, type, id }` (id = order/subscription/refund id) makes
  the mock build the Polar webhook envelope for that entity and POST it, Standard Webhooks-signed
  with `secret`, to `url`. Lets a script drive `PolarProvider.verifyWebhook` (and
  `webhook.receive`/`process`) against a real HTTP delivery instead of a hand-built request.

See `examples/live/polar-mock.ts` / `examples/live/polar_mock.py` for a full round trip: customer/
checkout/order/subscription CRUD, `changeSubscription` proving `resetAnchor` is ignored (no Polar
equivalent), cancel at-period-end vs. immediate, partial refund, idempotent usage ingestion,
`verifyWebhook` valid/tampered/stale-timestamp, and a renewal round trip where a mock-produced
`order.paid` webhook flows through the real `webhook.receive`/`process` + `lifecycle.onRenewalPaid`
+ `credits` grant and actually moves the in-memory ledger balance.

## PortOne (`tools/mocks/portone/server.mjs`)

PortOne ships no official mock server either, so this is a hand-rolled `node:http` mock of the
subset of the PortOne V2 REST API that `packages/providers/portone` calls: `GET /payments/{id}`,
`GET /payments` (list), `POST /billing-keys`, `POST /payments/{id}/billing-key`,
`POST /payments/{id}/cancel`, `POST /payments/{id}/schedule`, `DELETE /payment-schedules`.
developers.portone.io itself is JS-rendered and didn't yield full schemas via fetch, so the
request/response shapes here were taken from the real V2 OpenAPI spec instead — the
`portone-io/server-sdk` GitHub repo's `codegen/openapi.json` (fetched 2026-09-09), which is what
PortOne's own SDKs are generated from. Cross-checking the provider package against that spec
turned up real bugs (a wrong status literal, a misread response field, an endpoint that doesn't
exist, request bodies missing a required wrapper) — all fixed in
`packages/providers/portone/{ts/src/index.ts, py/src/boilpayment_portone/__init__.py}`; see
that package's `spec/portone.pseudo.md` 2026-09-09 note for the full list.

```bash
node tools/mocks/portone/server.mjs   # listens on PORTONE_MOCK_PORT (default 12212)
```

Requires `Authorization: PortOne test_...` (any secret starting with `test_`; anything else, or a
missing header, is a `401`); in-memory state.

Mock-only helper endpoints (prefixed `/__mock/` so they never collide with a real PortOne path, no
PortOne auth required):

- `POST /__mock/seed/payment` — injects a full `Payment` record directly, keyed by `id`. There's
  no way to reach every real status (`VIRTUAL_ACCOUNT_ISSUED`, `FAILED` with a specific `pgCode`, a
  virtual-account `method` for the refund-account test) purely through the billing-key charge flow
  this mock implements, so seeding fills that gap — the same role stripe-mock's built-in fixtures
  play for Stripe.
- `POST /__mock/sign` — `{ type, data, secret, staleSeconds? }` → `{ headers, body }`, computes a
  real Standard Webhooks signature without pushing it anywhere, so a script can build a
  tampered-body or stale-timestamp case locally by mutating what comes back before calling
  `verifyWebhook`.
- `POST /__mock/webhook` — `{ url, secret, type, data }` makes the mock POST a
  Standard-Webhooks-signed `{ type, data, timestamp }` envelope to `url`, signed with `secret`
  (`whsec_...` form, same algorithm as `PortoneProvider.verifyWebhook`/`verify_webhook`). Used for
  the real end-to-end delivery in the renewal round trip below.
- `GET /__mock/health` — liveness check.

See `examples/live/portone-mock.ts` / `examples/live/portone_mock.py` for a full round trip:
`confirmPayment` match/mismatch, `getPayment` for `PAID`/`VIRTUAL_ACCOUNT_ISSUED`/`FAILED` (with
normalized `pgCode` failure), billing-key issue + charge with an idempotent repeat (real PortOne
semantics: retrying an already-`PAID` `paymentId` returns `ALREADY_PAID`, not a double charge),
`schedulePayment` + `cancelSchedules`, partial refund and virtual-account refund without/with
`refundAccount`, `listPayments` with a client-side customer match (PortOne's filter has no
server-side customer-id field — confirmed from the OpenAPI spec, not left "best-effort"),
`verifyWebhook` valid/tampered/stale-timestamp, and a provider-scheduled renewal round trip where a
mock-produced `Transaction.Paid` webhook flows through the real `webhook.receive`/`process` +
`credits.topup` and actually moves the in-memory ledger balance. (PortOne's normalized webhook
never carries a `subscriptionRef` — it has no native subscription concept — so this path always
goes through `credits.topup`, never `lifecycle.onRenewalPaid`; that's a real contract fact, not a
simplification made for the mock.)

## Stripe renewals (`tools/mocks/stripe-renewals/server.mjs`)

`stripe-mock` answers every call with a fixed fixture, so it cannot hold one invoice's state across
its payment, a dashboard refund and a dispute. This mock keeps invoices, subscriptions and payment
intents (with an expanded `latest_charge`) that a test sets with `POST /__set`, and `POST /v1/refunds`
moves the charge's `amount_refunded`. Used by `apps/cli/test/generated-native-postgres.test.ts`.
